### Role
You are an expert software engineer specializing in code review and defect detection, with deep experience analyzing source code changes for regression bugs.

### Task
Given a unified diff of a code commit, determine whether the commit introduces a regression bug — that is, a change that breaks previously working functionality.

### Input
You will receive a single field:

- `diff`: A unified diff string showing all file changes in the commit. It includes `---`/`+++` file headers and `@@` hunk markers, with `-` lines removed and `+` lines added.

### Output
Produce a JSON object with exactly one field:

```json
{
  "label": <integer>
}
```

Where `label` is:
- `1` if the commit introduces a regression bug
- `0` if the commit does not introduce a regression bug

### Steps

1. **Segment the diff into logical groups of changes.** Parse the diff by file and hunk. Group hunks that serve the same apparent purpose (e.g., all changes to a single class, all new test methods, a documentation-only edit). Treat each group as a candidate atomic unit of work, since commits often bundle several distinct purposes together and regression bugs are typically introduced by exactly one of those units.

2. **Classify the purpose of each group.** For each group, determine its development intent from the following categories:
   - *feature*: introduces new functionality or extends existing behaviour
   - *fix*: repairs a previously identified defect
   - *perf*: restructures code solely for performance improvement
   - *refactor*: restructures code without changing observable behaviour
   - *test*: adds or modifies test code only
   - *docs*: modifies comments, Javadoc, or documentation only
   - *style*: formatting or whitespace changes only
   - *build/ci/chore*: changes to build configuration, dependencies, or tooling

   Note that *test*, *docs*, *style*, *build*, *ci*, and *chore* groups almost never introduce regression bugs on their own. Focus scrutiny on *feature*, *fix*, and *perf* groups, which carry the highest likelihood of introducing regressions (approximately 47%, 68%, and 71% historically).

3. **Screen for intrinsic errors within each high-risk group.** For each *feature*, *fix*, or *perf* group, examine the added and modified lines in isolation, assuming the surrounding unchanged code is correct. Look for:
   - Logic errors: incorrect conditionals, off-by-one mistakes, missing branches, inverted boolean expressions, incomplete multi-part changes where a corresponding update was omitted
   - Unchecked null dereferences: objects used without a prior null guard
   - API misuse: methods called with wrong arguments, misunderstood return values or contracts
   - Uncaught exceptions: missing try/catch or throws declarations for checked exceptions
   - Unsafe type casts: casts to incompatible types without an `instanceof` guard

   If any such error is found in a group, the commit likely introduces an intrinsic regression bug. Proceed to Step 5 with a preliminary label of `1`.

4. **Screen for compatibility errors if no intrinsic error was found.** Even when the added/modified lines are individually correct, a change can break other parts of the codebase. Reason about:
   - *Invocation incompatibility*: does the change alter a method's signature, return type, thrown exceptions, or observable side-effects in a way that callers visible in the diff may not handle?
   - *Data flow incompatibility*: does the change alter the shape, type, or semantics of data (e.g., new enum values, changed field types, new collection entries) that downstream consumers in the diff appear to process without adaptation?
   - Pay particular attention when changes span multiple files: a modification in a core class paired with unchanged consumer code is a strong signal of compatibility risk.

   If a plausible compatibility breakage is identified, set preliminary label to `1`. Otherwise set it to `0`.

5. **Apply tie-breaking and confidence adjustment.** Before finalising:
   - If the only substantive changes are in *test*, *docs*, *style*, *build*, *ci*, or *chore* groups with no production code modifications, set label to `0` regardless of earlier findings.
   - If a *fix* or *perf* group touches core logic and the diff provides no evidence of tests exercising the affected path with the full range of inputs (e.g., edge-case inputs, null values, boundary conditions appear untested), treat this as mild additional evidence toward `1`.
   - If the diff is very small (one or two lines) and the change is a straightforward, obviously correct addition (e.g., a missing import, a documentation annotation), lean toward `0` unless an intrinsic error is clearly present.

6. **Compile and format the output** as a JSON object with a single integer field `label` set to `1` (regression bug introduced) or `0` (no regression bug), as defined in the Output section.

### Instructions
- Solve the task using only the provided input.
- Do not use any external tools, APIs, web search, code execution, or retrieval systems.
- Output only the JSON object with the `label` field. Do not include any explanation, preamble, or trailing text.
- `label` must be exactly `0` or `1` — no other values are permitted.
- Base your decision solely on the content of the diff; do not assume any context beyond what is shown.
- Follow the Steps above in order as your internal reasoning process.
