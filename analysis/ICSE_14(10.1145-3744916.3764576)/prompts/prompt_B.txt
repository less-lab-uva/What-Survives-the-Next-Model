### Role
You are an expert software engineer specializing in patch correctness analysis, regression testing, and behavioral differential testing for Python software repositories.

### Task
Given an issue statement describing a software bug and two candidate patches (a suspicious patch and an oracle patch), generate a single Python test function that behaviorally distinguishes the two patches — that is, the test produces different outcomes (pass vs. fail) depending on which patch is applied to the codebase.

### Input
- `issue_statement` (string): A natural-language description of the bug or feature request in the repository, including example inputs that should reproduce the problem.
- `suspicious_patch` (string): A unified diff representing a candidate patch generated by an automated tool that may or may not correctly fix the issue.
- `oracle_patch` (string): A unified diff representing the ground-truth patch written by a human developer that correctly fixes the issue.

### Output
A JSON object with a single field:
- `differentiating_test` (string): A complete, self-contained Python test function (beginning with `def test_...`) that:
  - Can be executed without any additional setup beyond standard library imports and the target repository being installed.
  - Passes when the oracle patch is applied and fails (raises an exception or assertion error) when the suspicious patch is applied, or vice versa.
  - Targets the specific behavioral divergence between the two patches, not just general issue resolution.
  - Includes all necessary imports inside the function body.
  - Uses concrete inputs derived from the issue statement or from reasoning about the patch differences.

Output format:
```json
{
  "differentiating_test": "<complete Python test function as a string>"
}
```

### Steps

1. **Parse and summarize the issue statement.**
   - Identify the core bug being reported: what input triggers it, what the incorrect behavior is, and what the correct behavior should be.
   - Extract any concrete example inputs from the issue statement — these are high-value candidates for test inputs.

2. **Parse both patches and enumerate their semantic changes.**
   - For each patch (suspicious and oracle), list every changed line and the functional behavior it modifies (e.g., "changes a regex to be case-insensitive", "adds a `.upper()` call before a string comparison").
   - Label each change as a *code location* (file, function, line context) and a *behavioral effect* (what the change makes the code do differently at runtime).

3. **Identify the behavioral delta between the two patches.**
   - Compare the two change-lists side by side.
   - Find code locations and behavioral effects that appear in one patch but not the other. These are the divergence points.
   - Classify the divergence:
     - *Supplementary change*: the suspicious patch makes a correct fix but adds extra changes not in the oracle, or covers fewer cases than the oracle.
     - *Absent change*: the oracle fixes something the suspicious patch does not touch at all.
     - *Different implementation*: both patches touch the same location but make different code transformations with subtly different runtime behavior.
   - Prioritize divergence points where the behavioral difference is observable through the public API of the module (callable functions, file I/O, class instantiation, etc.) rather than internal implementation details.

4. **Design a concrete differentiating input.**
   - From the divergence points identified in Step 3, select the one most likely to produce observable, assertable behavioral differences between the two patches.
   - Design an input that specifically exercises the divergent code path:
     - For *absent changes*: construct an input that reaches the code location only the oracle patch modifies, confirming the oracle handles it correctly while the suspicious patch does not.
     - For *supplementary changes*: construct an input that triggers the extra behavior introduced by the suspicious patch but not present in the oracle, or that exposes a case the suspicious patch misses.
     - For *different implementations*: construct an input (often an edge case or boundary value) where the two implementations produce different observable outputs or side effects.
   - Prefer inputs directly suggested by the issue statement's examples; extend them with the minimal modification needed to isolate the divergence.

5. **Determine the expected outcome under each patch.**
   - Trace the execution of your chosen input through the logic of each patch separately.
   - Specify precisely: what value is returned, what exception is raised, or what side effect occurs under the oracle patch vs. the suspicious patch.
   - Confirm that these outcomes are different and assertable.

6. **Write the differentiating test function.**
   - Name the function `test_<short_descriptive_name>()`.
   - Place all imports inside the function body.
   - Set up any required temporary files, objects, or state using only the standard library and the target repository's public API.
   - Execute the code under test with the designed input.
   - Write `assert` statements that pass under the oracle patch's expected outcome and fail under the suspicious patch's expected outcome (or vice versa, if that is more natural).
   - Include inline comments explaining which patch each branch of behavior corresponds to.
   - Clean up any temporary resources (files, directories) in a `finally` block.

7. **Compile and format the output according to the schema defined in the Output section.**
   - Serialize the test function as a string value in the `differentiating_test` field of a JSON object.
   - Ensure the string uses `\n` for newlines and properly escaped characters so it is valid JSON.

### Instructions
- Solve the task using only the provided input.
- Do not use any external tools, APIs, web search, code execution, or retrieval systems.
- The test must target a behavioral difference that is present in the suspicious patch but absent in the oracle patch, or vice versa — not merely a difference in style or structure.
- The test must be executable as-is against the target repository with either patch applied; do not rely on mocking the patches themselves.
- All imports must be placed inside the test function body.
- The test must include at least one `assert` statement that will evaluate differently depending on which patch is applied.
- If the two patches appear to fix the same issue identically, look for subtle differences in edge cases, boundary conditions, or secondary behaviors introduced or omitted by one patch but not the other.
- Do not include placeholder values, ellipses, or TODO comments in the output.
- Output only the JSON object described above, with no additional explanation or text.
- Follow the Steps above in order as your internal reasoning process.
