# RISE

Single-LLM-call recreation of **RQ3** (translation accuracy on TPC-DS) from *RISE:
Rule-Driven SQL Dialect Translation via Query Reduction* (DOI 10.1145/3744916.3773257).

One call replaces RISE's whole pipeline: given a source PostgreSQL query, the oracle returns
the MySQL translation. Run for prompt A (black-box) and prompt B (informed). This is the
paper's own `SingleLLM` / `LLMTranslator` baseline, scored the way the paper scores it —
by executing both queries and comparing result sets.

## Prerequisites

- Python 3
- An Anthropic API key (`ANTHROPIC_API_KEY`) — for `main.py`
- Docker — for `evaluator.py` (it launches PostgreSQL 15 + MySQL 8)

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt
```

## Data

`inputs/tpcds/query*.sql` — the 99 source PostgreSQL queries (the only oracle input). The
TPC-DS *table data* is not an input; it is generated by the evaluator so it can execute both
queries and compare results. 

Note the replication package includes queries but not the actual data. Various generators external
generators are responsible for creating data to seed the DBs with. We were only able to generate
data for TPC-DS dataset so that is the result we compare to.

## Run

The script refuses to clobber outputs (fail-fast abort rather than overwrite). Back up or
remove any existing `outputs/output_*.jsonl` / `outputs/log_*.jsonl` first, then:

```bash
ANTHROPIC_API_KEY=<your key> python3 main.py
```

## Outputs (one of each per prompt variant A/B)

- `outputs/output_{A,B}.jsonl` — translations: `name, source_dialect, target_dialect, source_query, translated_query`
- `outputs/log_{A,B}.jsonl` — raw per-call log: `name, start_time, end_time, input_tokens, output_tokens, model, raw`

## Evaluation

`evaluator.py` is self-contained: it launches PostgreSQL 15 + MySQL 8 (Docker), generates
TPC-DS with DuckDB and loads identical data into both engines, runs the source query on
PostgreSQL and the translated query on MySQL, compares result sets, and tears the containers
down. Scored at **scale factor 0.1** — the paper does not specify the scale factor 
for the data generator but sf=1 was not computationally
feasible here (heavy MySQL queries do not complete; see the note in `evaluator.py`).

```bash
python3 evaluator.py        # results/results_{A,B}.json — accuracy + per-query pass/fail (A vs B)
python3 utils/usage.py      # logs/usage.json            — seconds elapsed + cost (A vs B)
```

## `utils/` (run from this directory)

Helper scripts kept separate from the core pipeline (`main.py`, `evaluator.py`). Paths are
fixed relative to this directory, so invoke them as `python3 utils/<script>.py`:

- `utils/prompt_generator.py` — regenerate `prompts/prompt_A.txt` + `prompt_B.txt` from the paper PDF + `prompts/meta_prompt.txt`.
- `utils/estimate_cost.py` — project the run cost via the free `count_tokens` endpoint (no spend).
- `utils/usage.py` — after a run, derive seconds + cost from the per-call logs → `logs/usage.json`.
