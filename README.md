# Ephemeral-SE

This repository contains the replication artifacts for a study of whether a
single prompt to a newer large language model can replace recent LLM-based
software engineering techniques. The study analyzes 35 ICSE 2026 papers. For
each paper, we identify the original technique's raw input and final output,
construct two single-call prompts, run the prompts on the selected benchmark
instances, and evaluate the generated outputs using the paper's original
metric or evaluation setup.

The repository is organized as a collection of paper-specific artifacts. Each
paper directory contains the local metadata, prompts, executor, evaluator,
outputs, results, and a paper-specific README when available.

## Research Questions

The artifacts support three main analyses:

1. **RQ1:** Given a software engineering task, how effectively does
   single-prompt inference on state-of-the-art LLMs compete with a recent
   software engineering tool?
2. **RQ2:** What factors make a technique more amenable to single-call LLM
   substitution?
3. **RQ3:** How much performance gain is achieved by embedding the original
   paper's methodology as reasoning guidance into the `P_w` compared to `P_b`?


## Categories and Outcomes

The study categorizes papers along two dimensions: task category and strategy
category. A **task category** captures what software engineering problem the
paper is trying to solve. A **strategy category** captures the main technical
idea or pipeline contribution the paper uses to solve that problem.

- **Task category:** the software engineering task performed by the paper, such
  as code generation, bug finding, repair, impact analysis, requirement
  formalization, log analysis, test generation, or verification.
- **Strategy category:** the primary technical strategy used by the original
  technique, such as knowledge grounding, feedback and validation, structured
  reasoning, search and selection, input/output control, domain-specific
  processing, or model adaptation.

A paper may receive multiple task or strategy labels when appropriate. The
category table is available in [`categorized_analysis.md`](categorized_analysis.md).

Outcome symbols:

- `+`: the single-prompt replacement outperforms the technique in the paper.
- `-`: the single-prompt replacement underperforms the technique in the paper.
- `+-`: mixed result; the single-prompt replacement outperforms only for some
  datasets or metrics.

## Prompt Variants

Each paper is evaluated with two prompt variants:

- **Black-box prompt(`P_w`).** Describes the task, input fields, output
  format, constraints, and at least one input-output example from the selected
  dataset.
- **White-box prompt(`P_b`).** Includes the same task specification as
  Prompt A, plus methodology-inspired guidance derived from the original
  paper's technique.

Both prompts are single-call replacements. They do not call external tools,
perform multi-turn interaction, or receive intermediate artifacts generated by
the original technique unless those artifacts are part of the raw dataset.

## Evaluation Design

For each paper, the evaluator was built to match the paper's target research
question and metric. Two broad evaluation styles appear in the artifacts:

- **Ground-truth comparison.** The dataset directly provides labels, reference
  outputs, affected elements, or other ground truth. The evaluator compares the
  LLM output against this reference using the paper's metric.
- **Execution or checking.** The output must be run or checked before a metric
  can be computed. These evaluators may run tests, compilers, coverage tools,
  semantic equivalence checkers, database engines, benchmark harnesses, or
  other paper-specific execution environments.

The evaluator scripts are paper-specific because each original technique
defines its own output format, metric, and evaluation protocol.


## Repository Layout

```text
.
├── analysis/
│   ├── README.md
│   └── ICSE_<id>(<doi>)/
│       ├── README.md
│       ├── paper.json
│       ├── paper.pdf
│       ├── prompts/
│       ├── main.py
│       ├── evaluator.py
│       ├── outputs/
│       └── results/
├── categorized_analysis.md
└── prompt_generator.py
```

Important files:

- [`analysis/README.md`](analysis/README.md): index of the 35 paper
  directories and paper titles.
- [`categorized_analysis.md`](categorized_analysis.md): task category,
  strategy category, and outcome for each paper.

Most paper directories follow this pattern:

- `paper.json`: local metadata and summarized evaluation information, including
  title, DOI, dataset, metric, original result, our results, and cost.
- `paper.pdf`: local copy of the paper used to construct prompts and
  evaluators.
- `prompts/`: Black-box and White-box Prompts.
- `main.py`: executor that loads dataset instances, sends the prompt-instance
  pair to the LLM, and writes extracted outputs.
- `evaluator.py`: evaluator that computes the paper-specific metric using the
  correct ground truth or execution setup.
- `outputs/`: raw and extracted model outputs.
- `results/`: evaluated results for both prompts.
- `requirements.txt`: paper-specific Python dependencies when needed.


## Running an Experiment

There is no single global command that runs all 35 papers because the original
papers use heterogeneous datasets, metrics, and evaluation environments. The
recommended workflow is to run a paper-specific artifact:

```bash
cd analysis/ICSE_<id>(<doi>)
pip install -r requirements.txt    # when the directory provides one
export ANTHROPIC_API_KEY=your_key_here
python3 main.py                    # exact arguments vary by paper
python3 evaluator.py
```

Always consult the paper-specific `README.md` before running a directory. Some
evaluators require Docker, Apptainer, benchmark downloads, hidden tests,
database containers, or external execution services.

## Notes and Limitations

- The artifacts are designed for replication of this study, not as official
  reproductions of the original papers.
- Some datasets are sampled because the study used a fixed LLM budget per
  paper.
- Some paper directories require external benchmark assets that are not stored
  in this repository.
- Some evaluators are expensive or slow because they reproduce execution-based
  evaluation setups.
- Generated outputs and evaluated results are checked in where available, so
  many analyses can be inspected without rerunning LLM calls.

## Useful Entry Points

- Start with [`analysis/README.md`](analysis/README.md) to find a paper
  directory.
- Read the paper-specific `README.md` before running `main.py` or
  `evaluator.py`.
- Use [`categorized_analysis.md`](categorized_analysis.md) for the final
  task/strategy/outcome table.
